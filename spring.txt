What are the different types of dependency injection in Spring Boot?
Constructor Injection: Passes dependencies via the constructor. Preferred for making dependencies explicit and ensuring immutability.
Setter Injection: Passes dependencies via setter methods. Useful for optional dependencies and flexibility.
Field Injection: Injects dependencies directly into fields. Simplifies code but makes dependencies less explicit and harder to test.

What is the difference between constructor injection and setter injection?
Immutability:
Constructor Injection: Promotes immutability by setting dependencies at the time of object creation.
Setter Injection: Allows for mutable dependencies, as they can be changed after object creation.
Mandatory vs. Optional Dependencies:
Constructor Injection: Ensures that all required dependencies are provided and initialized when the object is created.
Setter Injection: Allows for optional dependencies, as dependencies can be set or changed after the object is created.
Thread Safety:
Constructor Injection: Inherently thread-safe because dependencies are set once and cannot be modified.
Setter Injection: Requires additional synchronization if dependencies are changed after object creation.
Circular Dependencies:
Constructor Injection: Can lead to issues with circular dependencies.
Setter Injection: Can help resolve circular dependencies by setting dependencies after object creation.
Testing:
Constructor Injection: Easier to write unit tests because dependencies are provided through the constructor.
Setter Injection: Allows for easier mocking and stubbing of dependencies in unit tests.
Constructor Injection:
Use when you want to ensure that all required dependencies are provided and initialized at the time of object creation.
Use when you want to promote immutability and thread safety.
Use when you want to make the dependencies of a class explicit and mandatory.
Setter Injection:
Use when you have optional dependencies that can be set or changed after object creation.
Use when you need to resolve circular dependencies.
Use when you want to separate the construction of the object from the injection of dependencies.

What is transaction propagation in Spring Boot?
Transaction propagation in Spring Boot (and Spring Framework) defines how transactions interact with each other when multiple transactional methods are called. It specifies the behavior of a transactional method when it is invoked by another transactional method. Spring provides several propagation behaviors to control transaction boundaries and ensure consistent data integrity.
REQUIRED: Joins existing transaction or creates a new one if none exists.
REQUIRES_NEW: Always creates a new transaction, suspending any existing one.
SUPPORTS: Joins existing transaction if available, otherwise executes non-transactionally.
NOT_SUPPORTED: Always executes non-transactionally, suspending any existing transaction.
MANDATORY: Requires an existing transaction, throws an exception if none exists.
NEVER: Always executes non-transactionally, throws an exception if a transaction exists.
NESTED: Creates a nested transaction if an existing transaction is present, otherwise behaves like REQUIRED.

What is the circular dependency issue?
Circular Dependency Issue:
Occurs when two or more beans depend on each other, creating a cycle.
Can lead to bean initialization failure and application context startup failure.
Example:
BeanA depends on BeanB, and BeanB depends on BeanA.
Consequences:
Bean initialization failure (BeanCurrentlyInCreationException).
Application context startup failure.
Solutions:
Constructor Injection: Avoid using constructor injection for beans with circular dependencies.
Setter Injection: Use setter injection to break the circular dependency.
@Lazy Annotation: Use @Lazy to defer the initialization of one of the beans.
Redesign the Application: Refactor the code to eliminate the circular dependency.

Eager loading is a technique where related data is loaded from the database as part of the initial query. This means that all the necessary data is retrieved in a single query, reducing the number of database calls.
Ex: Fetching Order Data with Customer Data
Lazy Loading
Lazy loading is a technique where related data is loaded on demand, i.e., when it is first accessed. This means the initial query retrieves only the primary entity, and related data is fetched in separate queries as needed.
Ex: Fetching Comments on a post only when the comment button clicks.
What is the HTTP code for not found?
The HTTP code for "not found" is 404. It's a client error response status code that indicates that the server can't find the requested resource.
When using RESTful APIs, which HTTP status code range indicates that the client made an error?
4xx range specifically indicates that the client made an error. Common status codes in this range include:

What is idempotence in the context of HTTP methods?
Idempotence: The property of an operation where performing it multiple times has the same effect as performing it once.
Idempotent Methods: GET, PUT, DELETE, HEAD, OPTIONS.
Non-Idempotent Methods: POST, PATCH.
What is GET vs POST
GET and POST are two HTTP request methods that allow web interactions. 
GET: Used to retrieve data from a server or resource, such as for searching, filtering, or paging. The requested data is passed as query parameters in the URL, making the data visible. GET is ideal for searches and appending parameters in the URL, but it is less secure. 
POST: Used to send data to a server to create or update a resource, such as for submitting forms, modifying data, or file uploads. The data being sent is included in the body of the message, keeping it hidden and making POST more secure than GET. POST is also ideal for making complex API requests where the data is not easily represented in a URL.
What are the limitations of the GET method in HTTP?
Data Length Restrictions:
URL Length: GET requests append data to the URL, which can lead to length restrictions. Different browsers and servers have varying limits on URL length, typically around 2,048 characters. Exceeding this limit can result in errors or truncated data.
Security Concerns:
Sensitive Data Exposure: Data sent via GET is visible in the URL, making it less secure for transmitting sensitive information such as passwords or personal details. URLs can be logged in browser history, server logs, and network logs, potentially exposing sensitive data.
Caching:
Automatic Caching: GET requests are often cached by browsers and intermediate proxies. While this can improve performance, it may lead to issues with data freshness if the server's response changes frequently and the cache is not properly managed.
Idempotency:
Read-Only Operations: GET requests are intended for read-only operations and should not modify server state. Using GET for actions that change data (e.g., updating or deleting resources) violates the idempotent nature of GET and can lead to unintended side effects.
Limited Data Size:
Query String Limitations: The amount of data that can be sent in a GET request is limited by the maximum URL length. This makes GET unsuitable for sending large amounts of data or complex data structures.
Encoding Issues:
URL Encoding: Data sent in the URL must be properly encoded to ensure special characters are correctly interpreted. Improper encoding can lead to errors or misinterpretation of the data.
Visibility:
Bookmarking and Sharing: While the visibility of GET parameters can be useful for bookmarking and sharing URLs, it also means that any sensitive data included in the URL can be easily shared or exposed unintentionally.
How can you make GET requests more secure?
Avoid Sending Sensitive Data:
Do Not Include Sensitive Information: Avoid including sensitive data such as passwords, personal information, or payment details in the URL of GET requests. Use POST requests for transmitting sensitive data, as the data is included in the request body and not visible in the URL.
Use HTTPS:
Encrypt Data in Transit: Always use HTTPS to encrypt data transmitted between the client and server. HTTPS ensures that the data, including URLs and query parameters, is encrypted and protected from eavesdropping and man-in-the-middle attacks.
Implement Input Validation and Sanitization:
Validate and Sanitize Input: Ensure that all input received via GET requests is properly validated and sanitized on the server side to prevent injection attacks, such as SQL injection and cross-site scripting (XSS).
Use Secure Tokens:
Authentication and Authorization: Use secure tokens (e.g., JWT, OAuth tokens) for authentication and authorization. Ensure that tokens are transmitted securely and are not included in the URL. Instead, use HTTP headers to transmit tokens.
Limit URL Length:
Keep URLs Short: Avoid excessively long URLs by limiting the amount of data sent via GET requests. This reduces the risk of URL truncation and potential exposure of sensitive data.
Implement Rate Limiting:
Prevent Abuse: Implement rate limiting to prevent abuse and protect against denial-of-service (DoS) attacks. Rate limiting helps control the number of requests a client can make within a specified time period.
Use Content Security Policy (CSP):
Mitigate XSS Attacks: Implement a Content Security Policy (CSP) to mitigate the risk of cross-site scripting (XSS) attacks. CSP helps control the sources from which content can be loaded, reducing the risk of malicious scripts being executed.
Monitor and Log Requests:
Track and Analyze: Monitor and log GET requests to detect and analyze suspicious activity. Regularly review logs to identify potential security threats and take appropriate action.
Implement CORS Policies:
Control Resource Sharing: Use Cross-Origin Resource Sharing (CORS) policies to control which domains are allowed to access your resources. This helps prevent unauthorized access from malicious websites.
Use Secure Cookies:
Session Management: For session management, use secure cookies with the HttpOnly and Secure flags set. This ensures that cookies are only transmitted over HTTPS and are not accessible via JavaScript.

What are REST APIs and what are some best practices to write it?

Key Principles of REST:
Stateless: Each request from a client to a server must contain all the information needed to understand and process the request. The server does not store any client context between requests.
Client-Server Architecture: The client and server are separate entities that communicate over a network. This separation allows for independent evolution of the client and server.
Uniform Interface: REST APIs use standard HTTP methods (GET, POST, PUT, DELETE) and URIs to access and manipulate resources.
Resource-Based: Resources are identified by URIs, and operations are performed on these resources.
Layered System: A REST API can be composed of multiple layers, such as security, caching, and load balancing, which are transparent to the client.
Cacheable: Responses from the server can be cached to improve performance.
Best Practices: Use nouns for URIs, appropriate HTTP methods and status codes, JSON for responses, versioning, error handling, pagination, security, documentation, and HATEOAS.

HTTPS: Encrypt data transmitted between the client and server using SSL/TLS.
Input Validation: Validate and sanitize input data to prevent injection attacks.
Rate Limiting: Limit the number of requests a client can make to prevent abuse and DoS attacks.
Logging and Monitoring: Log and monitor API requests and responses to detect and respond to security incidents.

What is the role of HTTP methods in REST API?
HTTP methods play a crucial role in RESTful APIs by defining the actions that can be performed on the resources. Each HTTP method corresponds to a specific type of operation, and together they provide a standardized way to interact with the resources exposed by the API.
GET: Retrieve information about a resource. Safe, idempotent, and cacheable.
POST: Create a new resource. Not idempotent and generally not cacheable.
PUT: Update an existing resource or create a new resource if it does not exist. Idempotent and generally not cacheable.
DELETE: Delete a resource. Idempotent and generally not cacheable.
PATCH: Partially update an existing resource. Not idempotent and generally not cacheable.
OPTIONS: Describe the communication options for the target resource. Safe, idempotent, and cacheable.
HEAD: Retrieve the headers for a resource, without the response body. Safe, idempotent, and cacheable
